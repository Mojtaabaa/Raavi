# ADR-052 — Prompt Hub

**Status:** Accepted (2026-11-10)

## Context
Raavi's AI module could only summarise or question a single page. People wanted a library of reusable prompts (personal and shared), usable on pages with the page's content filled in, either run through the workspace's Managed AI or copied into another tool, with ratings, usage numbers, versions and forks. Constraints: tenant isolation (RLS), permission-correct context, one AI door, no new editor, no code execution in templates.

## Decisions
1. **Where**: inside the AI module (schema `ai`, same `AiDbContext`, RLS on every table): `PromptCategories`, `Prompts`, `PromptVersions`, `PromptEvents`, `PromptExecutions`, `PromptRatings`. Migrations `PromptHub` and `PromptHubRun`.
2. **Library & visibility**: a prompt is Personal (default) or Tenant-public. Only the owner edits. Sharing needs a published version (`Raavi:Prompts:MembersMayPublish`, default true; false = administrators only). Others see only the published version of public prompts; a public prompt that is Archived leaves the library. Administrators moderate (archive, deprecate, unshare) but cannot edit others' text; they cannot see personal prompts at all. Statuses: Draft, Published, Archived, Deprecated.
3. **Categories**: tenant-wide tree (`ParentId` + `SortOrder`, depth ≤ 8), independent of prompts. Managed by workspace administrators (`Raavi:Prompts:MembersMayManageCategories`, default false). Move/reorder refuses cycles and over-deep trees; delete needs an explicit strategy (to parent / to another category / uncategorized) and never deletes prompts or subcategories.
4. **Versions**: the prompt points to a draft and a published version. A draft is edited in place (autosaved by the UI); publishing makes the row immutable (the entity has no way to change it); editing a published prompt starts a new draft from the published text; restore copies an old version into a new draft (refused while a draft exists unless discarding is explicit); diff is a line LCS. Every execution/copy event references the exact version. Prompt rows carry a `Revision` concurrency token (409 `prompt.version_conflict`).
5. **Template language** (`PromptTemplate`): `{{name}}`, `{{name|default}}`, `{{#if name}}…{{/if}}`, `{{#unless name}}…{{/unless}}`. Pure data lookup — nothing is evaluated; values that look like tags are not expanded. Variables are the built-in catalog (providers) or the author's typed `input.*` definitions (text, number, boolean, date, select, multiselect; required/default/options) stored with the version. Publishing validates syntax and rejects unknown variables.
6. **Execution contexts** are `IPromptContextProvider`s registered in DI: page, selection, section, pages, space, jira-issue, generic; jira-project and templar-report are registered but report "unavailable" (the Jira connector reads single issues only; Raavi has no Templar integration). Providers read only through the module readers that apply the caller's rights (`IPageTextReader`, new `ISpaceInfoReader`, new `IIssueContextReader`); one inaccessible page fails the whole context. A prompt can only be used with the kinds it declares.
7. **Rendering** (`POST /prompts/{id}/render`) never records anything. It returns the final text, an estimate of tokens (≈ 1 per 3.5 characters), sources, where every variable's value came from, missing required values and `ready`. Size limit `Raavi:Prompts:MaxPromptChars` (100 000): over it the call fails with `prompt.context_too_large`; with `truncate: true` **and** `Raavi:Prompts:AllowTruncation` = true the biggest content values are cut with an explicit marker and a warning, never the instructions.
8. **Manual copy** makes no model call: the UI copies the (editable) rendered text and reports `POST /prompts/{id}/copied` (counted as a copy only). "I used it elsewhere" is a separate event (`PromptManualUseConfirmed`).
9. **Automatic execution** (`POST /prompts/{id}/execute`): needs the prompt's Automatic mode, an explicit `confirmed` consent, AI switched on; context is read and the text built **before** any row is stored or any call is made. Untrusted content variables are fenced as `<<<name … name>>>` with a system rule not to follow instructions inside. The call goes through the new `AiService.CompleteAsync` — the one door (settings, hourly limit, monthly cap, host policy, key, timeout, usage row) now shared with the page assistant. Started/Completed/Failed events and a `PromptExecution` row (version, tokens, duration, error class, sources without content, result text) are written; results are readable only by the person who ran the prompt. Results are never written into a page automatically: "save as new draft page" creates an unpublished page; "add to this page" appends to the page's **draft** after a confirmation dialog.
10. **Ratings**: 1–5 stars, one per person and prompt (unique index, updated in place), optional feedback kind (useful, accurate, needs-improvement, outdated) and comment; only public prompts, never by their owner; distribution and average on the prompt; comments visible to the owner, administrators and the author of each. **Usage numbers** come from `PromptEvents`: total uses = automatic executions + confirmed manual uses; copies are separate; previews are not events; unique users; averages; tokens; per-version breakdown; workspace analytics for administrators (date range). Cost is reported as "not available" (no pricing is configured).
11. **Fork**: copies the published text of a public prompt into the caller's personal library as an independent prompt with its own history and attribution (`ForkedFromId/Title`); later changes on either side do not propagate.
12. **Audit**: administrative actions (create, publish, visibility, archive/restore/delete, category changes, restore) are written as `PromptEvents` in the tenant's own tables. They are not written to the central tenant audit log because modules do not reference each other.

## Not covered / limits
- Sharing with specific users or groups (only Personal and workspace-public).
- Separate category permissions (view/create/edit/delete/move/manage): one switch — administrators, optionally all members.
- Retention: execution results and events are kept until the prompt is deleted; no automatic purge yet.
- No Templar integration; Jira context is key, title, status, type and link only (no description/comments); no Jira project context.
- Token counts before sending are estimates; truncation is off by default.
- Prompt feedback moderation, collections, chains, A/B tests are not built (designed-for only: events and versions carry the needed references).
- RTL/LTR rendering is covered by the shared layout and tests of the components, but no screenshot-based check was done.
