# ADR-049 — Smart search and retrieval-augmented answers (Phase 11b)

**Status:** Accepted (2026-11-09)

## Context
ADR-034 deferred retrieval over the whole wiki because it needed a vector store: SQL Server at compatibility level 130 has no vector type, OpenSearch and Docker are not available, and the product still lacked any body-text search. The requirement that stays unchanged: **a person may only ever get (or send to a model) what they may read** (SECURITY_ARCHITECTURE.md, AI context leakage).

## Decisions
1. **The index lives in SQL Server** (schema `ai`, RLS like everything tenant-owned): `ai.Chunks` (passages of ≤ 1 300 characters with title, space key and an optional embedding as unit-length little-endian float32 `varbinary(max)`) and `ai.IndexedPages` (page, version and embedding model that were indexed). No external service.
2. **Retrieval is hybrid and works without any AI.** Keywords: SQL `LIKE` over passages narrows (≤ 2 500 rows), memory scores (words found, title hits ×3, more distinct words, whole phrase, shorter passages first; question words such as "what is the" are ignored). Vectors (only when the workspace set an *embedding model*): the query is embedded and compared with every stored vector in slices of 400 rows (dot product, brute force, top 300 kept; ≈ O(chunks) per search — fine for tens of thousands of passages, to be replaced by an ANN store beyond that). The two rankings are fused with reciprocal rank fusion; the best passages are grouped per page. A provider failure falls back to keywords silently.
3. **Permissions — the index decides nothing.** Candidates are filtered at query time through `IViewableContentFilter` (Wiki module, the normal View evaluation for the current user), *before* anything is returned and before anything is put into a prompt. Restrictions added after indexing, trashed or archived pages therefore take effect at once; pages that left the Current state are removed from the index on the next run. Tests: a private space and a trashed page never appear in results, snippets, ask-sources or the prompt sent to the model; when nothing readable matches, no model call and no usage row happen (`ai.no_sources`).
4. **Indexing**: `IContentIndexSource` (Wiki) lists the current published versions and reads their text; `RagIndexer` (tenant job `AiIndexJob`, fan-out every 15 minutes by Workers, also "Index now"/"Rebuild" for administrators) re-chunks changed versions (`Chunker`: paragraphs, ~700 characters, long paragraphs split at sentence ends with overlap), embeds them (batches of 64, `POST {base}/embeddings`, same allow-listed host policy, key and error codes as chat — the transport was extracted to `AiTransport`), and deletes what disappeared. Slices of 150 pages, at most 4 minutes per run; a failing provider stops the run (keywords are already indexed, the pages stay pending for vectors); changing the embedding model re-embeds everything; a page without text counts as up to date. Embedding tokens are recorded in `ai.Usage` (feature `embed`, no text) and respect the monthly cap.
5. **Ask the wiki** (`POST /ai/ask`): the same rules as page questions (enabled + key + allowed host, hourly request limit per user, monthly token cap), the top readable passages (≤ `Raavi:Ai:MaxRagPassages` = 8) go into a numbered, delimited source block; the system prompt says the sources are untrusted data, asks for [n] citations and for an honest "not in the sources". The answer is returned with the sources (title, space, snippet); nothing about the question or the answer is stored (usage only counts tokens). Labelled machine-generated in the UI.
6. **API**: `GET /ai/search?q=&space=&take=`, `POST /ai/ask` (any signed-in member); `GET /ai/index`, `POST /ai/index/run`, `POST /ai/index/rebuild` (workspace administrators); settings gained `embeddingModel`. UI: "Smart search" page (`/search`: search as you type with highlighted words and a marker for meaning-based hits, ask mode with linked citations), AI settings with the embedding model and the index panel.

## Privacy and cost notes
Passage text is a copy of page content stored in the database (same protection as the pages, same tenant isolation, deleted with the page). With an embedding model the page text (not drafts) is sent to the tenant's provider to compute vectors; without it nothing leaves the installation for search. Rebuilding with a model re-sends all text.

## Addendum — Persian/Arabic folding (2026-11-10)
`SearchText.Normalize` folds letter variants (ي ى ئ → ی, ك → ک, ة ۀ → ه, أ إ ٱ آ → ا, ؤ → و), digits of every script to 0–9, Arabic marks and tatweel (removed), ZWNJ and no-break spaces (→ space) and case. It is applied to what is stored (`ai.Chunks.Norm` / `TitleNorm`, which the keyword search matches against; the original text stays for display and embeddings), to the query and to the scoring, so both sides always agree; migration `SearchNormalization` empties the index (policy off inside the transaction, like ADR-048) and the next run rebuilds it. Quick find (plain SQL on titles) searches the Persian and Arabic spellings of the query (`SearchText.Variants`). The browser has an equal twin (`textNormalize.ts`) for highlighting; both are tested against the same table. Not folded: stemming, other scripts' diacritics, the visually identical Latin/Cyrillic look-alikes.

## Not covered / limits
No ANN index (brute force); one embedding model per workspace; no reranking; drafts, comments, attachments' text, database rows and whiteboards are not indexed; search language is whatever the tokenizer sees (letters and digits — no stemming, no stemming); results show the best passage per page only; the 4-minute / 150-page slices mean a very large wiki needs several runs after the first start; real providers were not called (fakes only).
