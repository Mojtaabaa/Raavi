# ADR-035 — Live whiteboards with Yjs (Phase 11c)

**Status:** Accepted (2026-11-08). Extends ADR-011 (collaboration server) and ADR-030 (whiteboards).

## Context

ADR-030 delivered whiteboards that are saved as a whole with one ETag; two people editing meant a 412 for the second saver. The collaboration server (Hocuspocus + Yjs) already handles page drafts with tickets, permission re-checks, revocation and reset. This ADR adds boards as a second **document kind** on that infrastructure.

## Decisions

1. **Document address.** `{tenantId}:board:{boardId}:live` (pages stay `{tenantId}:page:{contentId}:draft`). `DocumentAddress` (API) and the document-name pattern (server) parse both kinds; a page ticket never opens a board and vice versa (the ticket is bound to the exact name).
2. **Yjs structure** (shared by server `collaboration/src/board.ts` and client `frontend/.../liveBoard.ts`): `elements: Y.Map<id, Y.Map<field, value>>` and `order: Y.Array<id>` (stacking order). One inner map per element, so concurrent edits of **different fields of one element merge** (one person moves it, the other recolours it); concurrent edits of the *same* field are last-writer-wins. The converter tolerates what concurrency can leave behind: duplicate ids in `order` (first wins), ids without an element (dropped), elements missing from `order` (appended by id — never lost). A fixture generated by the frontend binding is decoded by the server tests (`schema/board/live-board.fixture.json`), so the two implementations cannot drift apart silently.
3. **Persistence = the board row.** Boards are small (≤ 2 000 elements), so no update log and no snapshot compaction: with every store (debounce 2 s / max 10 s) the server sends the **full Yjs state** plus the converted element list; the API validates the list exactly like a REST save (`Whiteboard.SetLiveState` → the same normalisation: colours, sizes, point counts, ids), then stores validated `ElementsJson` and `YjsState` (varbinary, ≤ 8 MB) in one update and bumps the revision. The board is therefore always exportable/readable by REST without a Yjs decoder. If the API refuses the content (400), the server drops the in-memory document and resets every client (existing behaviour for pages). Loading resumes from `YjsState`; a board with none is seeded from `ElementsJson`.
4. **REST and live do not mix silently.** A whole-board save (PUT with ETag) replaces the elements, **clears `YjsState`** and asks the collaboration server to reset the document, so connected editors re-join from the new content; otherwise the stored live state would resurrect the old one. Live editors never use the whole-board save. Renaming has its own endpoint (`PUT /whiteboards/{id}/title`) that leaves elements and live state alone.
5. **Who may join.** Tickets (`POST /collaboration/tickets` with `kind: "board"`) are issued only for **editors** of the board's space (Edit right), tied to the user's interactive session and valid for 60 s; readers see the saved board and are never connected (live viewing for readers is deferred). Every reconnect fetches a fresh ticket, and the server re-checks live connections every minute through `/internal/collaboration/check`, which for boards verifies the session and the user's **current** rights (edit → keep, view → read-only, none → close with `raavi:revoked`).
6. **Client behaviour.** The editor decides at load: editor + collaboration enabled → join; the canvas stays read-only until the first sync (editing earlier would write a second copy of the seeded elements into the document) and falls back to the ordinary whole-board editing after 10 s or on any join error. In live mode there is no Save button (saving is continuous) and the header shows *connecting / live / offline* and who else is on the board. Edits are diffed into the smallest Yjs changes; undo/redo use `Y.UndoManager` tracking **only the user's own edits** (a collaborator's work is never undone). While offline, edits stay in memory and merge on reconnect (no IndexedDB cache — a reload while offline loses them).
7. **Limits and known gaps.** One collaboration-server node per document (Redis fan-out is not wired, as for pages); presence shows names only (no live cursors); a narrow pre-existing race — a store in flight at the moment of a reset — can still write once more (the API validates it, so the effect is a stale save that the next session overwrites); SVG export reads the stored list, which can lag a live session by up to the debounce (≤ 10 s).

## Not in 11c

Live view for readers, live cursors/selection, IndexedDB offline cache, multi-node (Redis) collaboration, per-element locking, board history or "version restore", conflict UI for same-field edits.
